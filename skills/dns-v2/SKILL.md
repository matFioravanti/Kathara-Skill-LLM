# Kathara DNS Configuration v2

Apply the requested DNS changes to the existing lab. Explicit requests take precedence over lab evidence and defaults within the boundaries below. Record material assumptions and block only items with no safe implementation.

## 1. Inventory and ownership

- Read lab.conf, effective Kathara defaults if accessible, shared.startup, device startups and any scripts they invoke, device files and current DNS/services. Map device → image, interfaces, assigned addresses, routes, forwarding and services. Collision domain labels do not determine IPs. Check plausible forward and return paths. Dynamic routing or unknown IPv6 defaults are UNVERIFIED; disabled or absent required transport is blocked.
- Creation owns topology, addressing and routing only when the user requests those changes. For a DNS task on an existing lab, Creation may supply inventory knowledge; its lab scaffolding, new prompt and runtime workflow do not apply. If creation is explicitly requested as a separate stage, finish that authorized stage before taking the DNS baseline. Agree on image/service ownership before edits; preserve existing non-DNS services and valid settings. An early or conflicting service start that DNS cannot repair without touching original lines is blocked.
- DNS changes are limited to assigned server image entries when needed, required files under its etc/bind, requested client etc/resolv.conf or etc/kathara-dns/resolv.conf, and DNS-only startup trailers on assigned devices. Preserve original startup lines, unrelated zones and files, shared.startup, devices, links, interfaces, MACs, addresses, routes, forwarding, IPv6 flags and routing daemons. Never run ip link set up or replace routing/controller images. Keep a before-state outside the lab, including modes and symlinks, for comparison and rollback.

## 2. Plan before writing

- Extract requirements, prohibitions and exact RRsets. Input aliases: authoritative/auth/ns, local_ns/ldns/recursive, records/hosts and secondary/slave. When supplied in the task, test.applications.dns supports authoritative: {zone: [server_ip]}, local_ns: {resolver_ip: [client]}, records: {TYPE: {fqdn: [values]}}. test.ip_mapping cross-checks actual addressing; test.reachability identifies requested paths. Use only the task prompt, initial lab files, authorized Skills and technical references allowed by the protocol. Do not search for or read correction.yaml, historical results, checker reports, reference solutions or other runs. Structured task data does not authorize access to benchmark solutions.
- Inventory each zone with primary/secondary owners, real IPs, SOA, apex NS and their A/AAAA, closest served parent, delegation/glue and required RRsets. Place RRsets in the deepest authoritative suffix. Preserve names and exact values/cardinality, apart from DNS normalization. Add only requested or operationally necessary records and zones.
- Prefer explicit devices/IP owners, then existing DNS evidence and suitable reachable devices. Never repurpose an explicitly client-only device. Use actual usable owned IPs for NS/glue/hints, transfers and resolver endpoints, based on relevant routes and interfaces. Exclude link-local IPv6 and loopback for published roles. Explicit record values may be external if requested. Prefer IPv4 by default if viable; IPv6 transport and AAAA data are independent. Preserve requested RRsets even if a transport is blocked; deliver independent feasible pieces and report PARTIAL.
- Enumerate clients and their intended resolver address(es) before writing. If the prompt names specific clients, use those; otherwise select eligible non-DNS host devices, respecting exclusions and existing roles. Include routers as clients only when explicitly requested. Prefer the explicit mapping, then reachable subnet/route evidence or a unique suitable resolver. Check real ownership and a plausible return path; never substitute an authoritative-only server or a guessed IP. Identify the effective resolver source and last writer for each client, including shared.startup, device startup, sourced scripts and obvious package/network hooks. Trace static command order; report unresolved branches, substitutions or possible late rewrites as UNVERIFIED. Mark blocked requirements before editing.

## 3. Configure and verify each BIND server

- Resolve effective image/unit: device [image] overrides configured Kathara default. Preserve a compatible BIND image/tag. Replace core only on an assigned DNS server; when other services are required, verify that the replacement supports them too. Keep unknown/routing/controller images; an explicitly assigned router may serve DNS only with existing compatible BIND and a free port 53. Check for dnsmasq and other listeners.
- When creating a configuration, consult [BIND templates](references/bind-templates.md) for the required role only. Resolve named.conf and includes to actual container paths. Primary zones use files under /etc/bind (e.g. db.root for ".", db.<zone> otherwise); secondary files under /var/cache/bind are populated by transfer. Match primary addresses, transfer ACLs, notify sources and return paths. Avoid duplicate options/zones and default-zone includes that conflict with the artificial root. Preserve unrelated options and zones. Use syntax supported by the image (e.g. type master/slave, masters); avoid obsolete dnssec-enable/dnssec-lookaside.
- Authoritative roles use recursion no. Recursive resolvers use recursion yes and no authoritative zones unless a mixed design was explicitly requested and can be validated with isolated role settings. An authoritative artificial root serves zone "." with type master, file db.root, recursion no, SOA, apex NS and required delegations. A recursive resolver uses zone "." with type hint, file db.hints and recursion yes; hints contain the artificial root apex NS and matching owned addresses. Keep resolvers free of authoritative lab zones except an explicitly validated alternative architecture. No public root hints or unrequested forwarders. For an unsigned artificial root use dnssec-validation no. Preserve explicit DNSSEC requirements; block if signing/trust cannot be configured and checked. Disable empty-zones where they mask requested reverse zones. Match allow-query, allow-recursion/cache ACLs and listen addresses to clients/peers and transport; allow any for recursion only when necessary in an isolated lab. Honor explicitly requested forwarding (including forward only if no fallback is intended).
- Trace the effective startup from shared to device. Require one effective BIND activation after network/address/route prerequisites (usually systemctl start named; verify any legacy bind9 unit). Preserve a valid existing start. If the only immutable start precedes networking and the existing design supports it, the v1 exception is one final restart after networking, which is the sole effective activation with final configuration. Block if a command prevents reaching the trailer or conflicts with this sequence. Never add a duplicate start or silently accept an unresolved start. A process is not evidence of loaded zones.

## 4. Check zone and client data

- Each primary zone has one SOA and an apex NS set; every NS serves that zone and has usable address data where required. Use absolute names, root SOA RNAME hostmaster., serial 1 for new zones, advance existing serial only for changed zone data. Ensure multiple primaries agree; confirm secondary transfer configuration statically and mark its loaded state unverified.
- Follow each chain from the artificial root through the closest served parents. The parent delegation NS set matches the child apex NS set. For NS inside the delegated child, include required A/AAAA glue matching the child's authoritative addresses for the feasible/required transport families. Out-of-bailiwick NS needs an independently resolvable path; do not invent glue. Check for occluded data, cycles, duplicate zones and root NS names under delegated TLDs. Ensure no unrelated records below cuts in parent files. Check requested A/AAAA/MX and any other requested records; NS/MX must not target aliases, CNAME cannot coexist with other data, MX/SRV targets must resolve. Reverse only when requested (in-addr.arpa or ip6.arpa, absolute PTR targets); require a specified supported design for classless IPv4. No default reverse, secondaries, search lists or forwarding.
- For every client verify that the nameserver configuration persists through boot. If no startup or known hook writes it, verify mount/copy semantics, target symlinks, effective image behavior and write order before accepting etc/resolv.conf as persistent. File existence alone is insufficient. If persistence cannot be established, or a startup writes the file, prefer a single managed DNS write at the end of device startup when permitted and safe. Write etc/kathara-dns/resolv.conf and append once, or reuse an existing managed final write: `cat /etc/kathara-dns/resolv.conf > /etc/resolv.conf`. Preserve unrelated options and comments and original startup lines, and verify there is no later writer. If a safe final write is unavailable, report persistence as UNVERIFIED and block any unsafe edit. Put intended usable nameservers first (at most three), avoiding 127.0.0.1 and ::1 unless a requested local resolver is configured, listening on that address, and its operation is verified separately. Treat unknown local runtime as UNVERIFIED. Keep existing unrelated DNS intact; reruns of an unchanged request must be byte-identical.

## 5. Mandatory final static gate

Re-read final files and dependencies against the requested inventory. Complete all four gates, each with PASS (executed and passed), FAIL (a concrete defect), or UNVERIFIED (not executed or insufficient evidence). A defect takes precedence over unknown checks; a gate passes only if every applicable check was performed and passed.

- **G1 — Client Resolver Gate.** For every client verify expected resolver ownership/IP, persistent resolv.conf, last identifiable writer and loopback eligibility. Trace boot behavior; unresolved writers or persistence are UNVERIFIED.
- **G2 — BIND Service Gate.** For each server verify effective image/BIND availability, named.conf/includes/zone paths, preserved valid startup, activation order and idempotence. Run named-checkconf and named-checkzone when available in a matching offline path/version context; named-checkconf -z requires that environment too. Record actual outcomes. Missing tools yield UNVERIFIED, never proof of an invalid configuration. A running process does not establish zone loading.
- **G3 — DNS Hierarchy Gate.** Verify every required zone, SOA/apex NS and address, parent delegation/glue, root role/hints, exact requested A/AAAA/MX/other RRsets, complete resolution chains, unserved zones, cycles and role/ACL settings.
- **G4 — Lab Integrity Gate.** Compare the full lab with the baseline, including modes/symlinks. Preserve topology, addresses, routes, interfaces, non-DNS services and original startup lines. Permit only scoped DNS files, image fields and DNS trailer changes; review their contents too.

For regular hierarchies use [the semantic precheck](references/static-audit.md) on observations derived from actual files; use the manual gate for shell constructs, BIND includes, secondary/runtime state and other conditions outside its scope. If a check fails, do one focused repair pass and recheck; roll back invalid changes and dependencies that remain unsafe and report unresolved items. Preserve unrelated work.

Keep validation offline. Do not run kathara lstart, kathara exec, dig or other network queries. Dynamic validation belongs to the external checker. Report `runtime: NOT_RUN` and what still needs validating externally (boot, actual client resolver, authoritative zone load or transfer, recursive answers and required transport). Static checks never establish runtime success.

Report compactly: `Status: COMPLETE|PARTIAL|IMPOSSIBLE; G1/G2/G3/G4: PASS|FAIL|UNVERIFIED; static: PASS|FAIL|UNVERIFIED; runtime: NOT_RUN`, role/zone/client mappings, changed paths, delegated zones, and blocked or unverified items with reasons. Aggregate static gates with FAIL precedence, otherwise UNVERIFIED if any gate is unknown, otherwise PASS. Configuration completion is separate: COMPLETE means every requested configuration item is implemented with no known defect or unreachable dependency; PARTIAL means blocked/incomplete items; unavailable validation tools affect verification rather than proving a configuration defect; IMPOSSIBLE leaves the lab untouched.
